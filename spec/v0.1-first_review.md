# BP-Train v0.1 Code Review

Reviewed against: `v1-detailed-spec.md` (post-answers-3 state), `spec_review.md`,
and the live `bpbench` 0.1.0 API.

All three tests pass. The implemented scope is the preparation pipeline
(Phases A and B). No training, no wrapper, no model abstraction yet — those are
not reviewed here.

Every finding below was verified by running the code or tracing through it
numerically. Claims that appeared in an earlier draft but did not hold up under
verification have been removed or corrected.

---

## 1. Architecture and Structure

The four-file layout (`prepare.py`, `controls.py`, `validation.py`, `custom.py`)
maps cleanly onto the spec's responsibility split. The public `__init__.py`
surface is minimal and correct. The data flow in `prepare_artifact` follows
the spec's §9.2 processing steps accurately.

No major structural complaints.

## 2. Bugs and Correctness Issues

### 2.1 `build_bolus_sources` — spurious pre-event feed ramp (Medium)

**Location:** `controls.py:build_bolus_sources`, lines 280–313.

Verified numerically: for a bolus event at `t=5.0` on a process starting at
`t=0`, the feed rate at `t=2.5` is `0.2` (non-zero) when it should be `0`.

The cause: the time-value list starts with `(t_start, 0)`. The bolus event then
appends `(event_time, rate)`. `_make_source_from_xy` uses `np.interp`, which
linearly interpolates between consecutive points — so the segment from
`(t_start=0, 0)` to `(event_time=5.0, rate)` creates a gradual ramp-up over the
entire pre-event period. With multiple bolus events, the background feed rate
drifts upward between every pair of events.

The V1 runtime wrapper will see a non-zero feed-rate control before any bolus
event occurs and will compute incorrect dilution/transport terms for the entire
pre-event period.

For `input.json` there are no non-continuous `FeedVolumeChange` entries, so the
bug is dormant. It will activate on any dataset that has bolus feeds.

The correct approach: insert a `(event_time, 0)` point immediately before
appending `(event_time, rate)`, ensuring the function stays at zero until the
ramp begins.

### 2.2 `get_shortest_time_diff` — degenerate ramp_duration from floating-point near-duplicates (Medium)

**Location:** `controls.py:get_shortest_time_diff`, lines 210–219.

For `input.json`, `ramp_duration` is `1.06e-7` hours (≈ 0.38 ms). This comes
from `process.time_axis.end = 12.0277...78` and the last online data point for
X, P, G at `12.0277...67` — the same timestamp represented with slightly
different floating-point precision. Their difference is `1.06e-7` hours.

The effect: every `V_sample_acc` ramp window in `step_ts` is `1.06e-7` hours
wide. The ODE solver's step-size controller receives guidance boundaries
essentially at `t` and `t + 1e-7`, a window far below any realistic integration
step. Whether the solver ignores or acts on such guidance depends on the backend,
but it is clearly unintended and could cause performance degradation.

`_collect_time_axis_points` mixes `process.time_axis.start/end` with all online
data timepoints and event timepoints. The minimum diff across this union is not
a stable proxy for "the shortest meaningful online interval". A more robust
strategy: either compute the minimum diff from only the process-variable online
data (excluding the time-axis boundary points), or enforce a minimum floor on
`ramp_duration` (e.g. one hundredth of the total process duration).

### 2.3 Confusing guard logic in `select_control_sources` with latent edge case (Low)

**Location:** `controls.py:select_control_sources`, lines 327–334.

```python
if isinstance(volume_change, FeedVolumeChange) and not volume_change.is_continuous:
    continue
if not volume_change.is_controlled:
    continue
if not getattr(volume_change, "is_continuous", False):
    continue
```

The first guard is redundant: the third guard already catches any non-continuous
entry. More importantly, a `SampleVolumeChange` with `is_continuous=True` and
`is_controlled=True` passes all three guards and lands in `volume_sources`. This
is almost certainly unintended. The latent defect does not trigger in `input.json`
(all `SampleVolumeChange` entries are non-continuous and non-controlled), but the
logic is harder to maintain than a single explicit check.

### 2.4 `_piecewise_linear_derivative` — right-side derivative at knot points (Low)

**Location:** `controls.py:_piecewise_linear_derivative`, line 56.

```python
indices = np.searchsorted(xp[1:], x, side="right")
```

At a knot point exactly on a breakpoint, this returns the slope of the segment
**after** the knot (right-side derivative). For a bolus ramp ending at
`ramp_end`, the stored derivative at that grid point is 0 (post-ramp slope)
rather than the ramp's own slope. This is internally consistent but may surprise
downstream code that assumes left-continuous derivatives.

Currently `control_derivatives` has no downstream consumer, so this is
theoretical. Worth documenting for when derivatives are first used.

## 3. Design Issues

### 3.1 All input.json processes fail bpbench validation — silently (High)

Running `validate_raw_collection` on `input.json` with `strict=False` produces
`ok: False` for all 12 processes. The failure messages are:

```
'No dynamic state variables found in reactor medium — check skipped'
'Reactor medium has no components — cannot verify biomass presence'
```

These are expected for this dataset (empty `reactor_medium.components`; see
`bpbench-api-notes.md §7`). But the default `strict=False` means `prepare_artifact`
completes successfully, stores the failure report in metadata, and writes a
`prepared.json` without any user-visible warning.

The existing test `test_prepare_artifact_writes_bp_train_metadata` passes on
this dataset and does not check `metadata["bp_train"]["bpbench_validation"]`,
so the silent failure goes unnoticed in CI.

Options: emit a warning when any process fails; or make `strict=True` the default
for a new prep run and require an explicit opt-out.

### 3.2 Cross-process control name consistency is not validated (Medium)

**Location:** `prepare.py:prepare_artifact`.

`select_control_sources` runs independently per process. For `input.json` no
process variable has `is_controlled=True`, so every process yields an empty
control list — trivially consistent. The issue will emerge as soon as a
`custom.py` sets `is_controlled=True` selectively, which the custom-order test
already does.

The test `test_prepare_artifact_respects_custom_control_order` sets both `CF`
and `T` as controlled for all processes uniformly. But nothing prevents a
researcher from writing a `custom.py` that marks `CF` as controlled in `DoE1`
and `BF` in `DoE2`. The padded control tensor would then have different semantics
per row, and the model would silently receive wrong inputs.

A cross-process consistency check after the hook loop — asserting that all
processes yield the same ordered control names — would catch this before training.

### 3.3 `step_ts` variable length across processes, no padding (Medium)

**Location:** `prepare.py:prepare_artifact`, line 195.

`step_ts` is stored per process as a plain list with variable length (different
numbers of sampling events per process). When downstream solver code takes
`step_ts` as a JAX array across all experiments, it will require either ragged
handling or padding with a mask. Neither exists in the current metadata.

### 3.4 Dead fallback code in `build_dense_payload` (Low)

**Location:** `controls.py:build_dense_payload`, lines 409–410.

```python
if not sources:
    sources = [build_sample_acc_source_default(process)]
```

In the current integration, `prepare_artifact` always passes at least the
`sample_source` entry. This fallback never executes. It also has inconsistent
semantics: `spreads` would not contain the sample-acc source, so the refinement
loop would use a spread of `1.0` for it. Remove or make consistent.

### 3.5 No guard against duplicate `V_sample_acc` in source list (Low)

**Location:** `prepare.py:prepare_artifact`, line 184.

If a user's `transform_controls` adds a `ProcessVariable` named `"V_sample_acc"`
with `is_controlled=True`, it will appear in `control_sources`, and the explicit
`sample_sources` append adds a second. The `control_names` list contains a
duplicate and `sample_acc_index` points to the wrong entry. No deduplication or
assertion exists.

### 3.6 `resolve_config` does not validate `get_config()` return type (Low)

**Location:** `custom.py:resolve_config`, line 32.

```python
resolved.update(dict(module_config))
```

If `get_config()` returns a dataclass instance instead of a dict, `dict(dataclass)`
raises a non-descriptive `TypeError`. A clear error message here (`"get_config()
must return a dict or None"`) would save debugging time for researchers.

## 4. Code Quality and Minor Issues

### 4.1 `_make_source_from_xy` extends single-point time series by `+1.0`

**Location:** `controls.py`, lines 125–127.

```python
times = np.asarray([times[0], times[0] + 1.0], dtype=float)
```

The extension duration `1.0` is arbitrary and not related to the process time
axis. For processes shorter than 1 hour, the extended point falls outside the
domain. Extrapolation via `np.interp` uses the boundary value, so there is no
numerical error, but the extension is misleading and should use `process.time_axis.end`
or at least the process duration.

### 4.2 `compute_signal_spreads` does an unnecessary Python list round-trip

**Location:** `controls.py`, line 383.

```python
values_by_name.setdefault(source.name, []).extend(source.values.tolist())
```

`source.values` is already a NumPy array. Converting to a Python list and later
re-wrapping with `np.asarray(...)` is wasteful. Direct `np.concatenate` across
all sources per name would be more efficient.

## 5. Tests

### 5.1 Tests use a fragile relative path (Medium)

**Location:** `tests/test_prepare.py`, lines 11, 18, 55.

```python
load_raw_collection("input.json")
prepare_artifact("input.json", output)
```

This depends on pytest being invoked with `bp-train/bp-train/` as the working
directory. Running from the repo root breaks with `FileNotFoundError`. Prefer:

```python
INPUT_JSON = Path(__file__).parent.parent / "input.json"
```

### 5.2 Integration test assertions are too shallow and miss the silent validation failure (Medium)

**Location:** `tests/test_prepare.py:test_prepare_artifact_writes_bp_train_metadata`.

The test passes on a dataset where all 12 processes fail bpbench validation (see
§3.1). It does not check `metadata["bp_train"]["bpbench_validation"]`, so CI
gives a green light while the underlying data quality issue goes unreported.

Additional assertions that should exist:
- `bpbench_validation` reports are all `ok: True` (or the test should explicitly
  acknowledge the known failure with a skip or xfail).
- `dense_grid` is strictly increasing within the active `grid_length` entries.
- `V_sample_acc` column in `control_values` is non-decreasing.
- `step_ts` entries are all within `[time_axis.start, time_axis.end]`.
- `control_derivatives` has the same shape as `control_values`.

### 5.3 Missing test: `V_sample_acc` correctness (High)

The spec §19.1 requires: "default `V_sample_acc` construction works as expected".
No such unit test exists. A test should:

- build a `BioProcess` with at least two `SampleVolumeChange` events at known times,
- call `build_sample_acc_source_default`,
- assert the result is non-decreasing,
- assert the final accumulated value equals the sum of all `abs(delta_V)` values,
- assert `step_ts` contains both ramp start and ramp end for each event.

### 5.4 Missing test: bolus ramp integrated amount and shape (High)

`build_bolus_sources` is completely untested, and the pre-event spurious ramp bug
(§2.1) would be caught immediately by a test that:

- builds a `BioProcess` with one `FeedVolumeChange(is_continuous=False, is_controlled=True)`,
- calls `build_bolus_sources`,
- asserts feed rate is exactly `0` before `event_time`,
- asserts the integral of the rate over `[event_time, ramp_end]` equals the intended `delta_V`.

### 5.5 Missing test: dense-grid refinement respects `max_rel_error` (High)

`build_dense_payload`'s refinement loop is untested. A test should:

- build a `SignalSource` from a known non-linear signal (e.g. a sine or a pulse),
- call `build_dense_payload` with a specific `max_rel_error`,
- reconstruct the signal from the returned grid using `np.interp`,
- assert the max reconstruction error is below `max_rel_error * spread`.

### 5.6 Missing test: fail-fast on missing required control (Medium)

No test calls `prepare_artifact` with a `required_control_names` that includes a
non-existent variable and verifies the resulting `ValueError`. This is a primary
fail-fast requirement from the spec (§9.3).

### 5.7 Missing test: cross-process control name consistency (Medium)

No test exercises the scenario where two processes end up with different
`control_names` (see §3.2). Once the validation is added, a regression test
should cover it.

### 5.8 `test_prepare_artifact_respects_custom_control_order` — direct dataclass mutation (Low)

**Location:** `tests/test_prepare.py`, lines 44–46.

```python
process.process_variables['CF'].is_controlled = True
```

Direct mutation of a bpbench dataclass. If bpbench switches to `frozen=True`
this breaks silently with `FrozenInstanceError`. The canonical approach is to
replace the field via `dataclasses.replace` and rebuild the `process_variables`
dict. This also sets a bad precedent for researcher-facing example code.
